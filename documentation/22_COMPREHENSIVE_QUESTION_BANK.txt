SECTION 1: BASIC & FOUNDATIONAL QUESTIONS
--------------------------------------------------------------------------------

Q1: What is RAG and why is standard RAG vulnerable in enterprise settings?
- Simple Answer: Retrieval-Augmented Generation combines information retrieval with an LLM to
  generate answers from private documents. Standard RAG is vulnerable because it stores unencrypted
  plaintext in vector databases, has no tamper detection, and cannot verify search completeness.
- Detailed Technical Answer: In standard RAG, parsed chunks reside as raw strings in vector databases
  (e.g., Pinecone, Qdrant, Chroma). If the database or network is breached, all corporate IP is
  exposed. Furthermore, standard RAG implicitly trusts vector search results: if an attacker modifies
  a chunk, the LLM ingests it as ground truth, enabling indirect prompt injection and data poisoning.
- Code Reference: See `core/document_ingestion.py` and `02_PROBLEM_STATEMENT_OBJECTIVES_AND_CONTRIBUTIONS.txt`.

Q2: What is the primary novelty of this project?
- Simple Answer: This project introduces an Asymmetric Verifiable RAG architecture that verifies
  every chunk through a 5-Gate Zero-Trust pipeline using AES-256-GCM encryption and Two-Tier Merkle
  Mountain Range (MMR) cryptographic proofs before the LLM can see the text.
- Detailed Technical Answer: The core innovation is decoupling vector search from data verification.
  The vector database only stores encrypted ciphertext and high-dimensional vectors. Integrity is
  mathematically proven via Two-Tier MMR inclusion paths ($O(\log N)$), while search completeness
  is verified using Voronoi Dynamic Boundary Verification (DBV), introducing zero retrieval degradation.

Q3: What embedding model and vector database does the project use?
- Simple Answer: It uses `BAAI/bge-small-en-v1.5` (384 dimensions) and the Qdrant vector database.
- Detailed Technical Answer: `BAAI/bge-small-en-v1.5` is loaded via `SentenceTransformer` in
  `core/embedding_service.py`. It produces 384-dimensional L2-normalized vectors. Qdrant manages
  tenant-isolated collections (`org_<id>_collection`) with HNSW cosine distance indexing.

SECTION 2: CRYPTOGRAPHY & SECURITY QUESTIONS
--------------------------------------------------------------------------------

Q4: How does AES-256-GCM work and why was GCM mode chosen over CBC?
- Simple Answer: AES-256-GCM is an Authenticated Encryption with Associated Data (AEAD) cipher that
  provides both confidentiality and tamper detection using a 128-bit authentication tag.
- Detailed Technical Answer: GCM combines Counter (CTR) mode encryption with Galois Message
  Authentication Code (GMAC). In GCM, each chunk receives a unique 96-bit nonce (`os.urandom(12)`).
  The tag is computed using polynomial multiplication in $\text{GF}(2^{128})$. Unlike CBC, GCM
  requires no padding (eliminating padding oracle attacks) and verifies integrity in hardware
  before plaintext parsing. In our benchmarks, encryption executes in 0.0188 ms per chunk.
- Code Reference: `crypto/encryption.py`, class `AESGCMEncryption`.

Q5: What is a Merkle Mountain Range (MMR) and how does it differ from a standard Merkle tree?
- Simple Answer: An MMR is an append-only collection of binary Merkle trees that allows adding
  new leaves in $O(\log N)$ time without rebalancing or recalculating the entire tree.
- Detailed Technical Answer: Standard Merkle trees require $2^k$ leaves and dynamic rebalancing
  when new leaves are appended. An MMR represents leaf count $N$ as a sum of powers of 2.
  Each power of 2 corresponds to a balanced peak. The overall root is computed by "bagging"
  the peaks from right to left. Chunks prove their inclusion via an $O(\log N)$ path of sibling
  hashes against an immutable Enterprise Cloud Root.
- Code Reference: `mmr/core.py`, `mmr/cloud_mmr.py`, `mmr/proof.py`.

Q6: What is Dynamic Boundary Verification (DBV) and what attack does it stop?
- Simple Answer: DBV geometrically checks whether vector search probed all required Voronoi clusters,
  stopping "Omission Attacks" where critical context is skipped.
- Detailed Technical Answer: Approximate Nearest Neighbor (ANN) indices use Inverted File (IVF)
  partitioning. If search parameters are restricted, mandatory clusters that overlap the query
  radius $r_k$ are omitted. DBV computes Euclidean distance between query vector $\mathbf{q}$ and
  pre-calculated centroids `ivf_centroids.npy`. If a required cluster was not probed, Gate 3 halts
  with `IVF_BOUNDARY_INCOMPLETENESS`, preventing omission hallucinations.
- Code Reference: `verification/boundary_validation.py`.

Q7: What happens if an attacker modifies a single character in the vector database?
- Simple Answer: Gate 2 detects the hash mismatch against the Merkle Enterprise Root, Gate 4 fails
  GMAC tag authentication, and the pipeline halts immediately with `MMR_TAMPERED`.
- Detailed Technical Answer: Even a 1-bit flip alters the SHA-256 chunk hash completely due to the
  avalanche effect. When Gate 2 recalculates the peak path, the computed root $R^*$ does not match
  `enterprise_root`. Furthermore, the 16-byte Galois GMAC tag fails in AESGCM. The system halts
  with zero plaintext emitted to the LLM. 200 out of 200 tampering trials were detected (100.0%).
- Code Reference: `main.py` lines 1450-1510; `benchmark_results.json`.

SECTION 3: RAG ARCHITECTURE & RETRIEVAL QUESTIONS
--------------------------------------------------------------------------------

Q8: What advanced RAG techniques are genuinely implemented in your project?
- Simple Answer: Corrective RAG (CRAG), Self-RAG reflection tokens, Reciprocal Rank Fusion (RRF),
  Cross-Encoder reranking, FlashRank compression, and Lost-in-the-Middle context reordering.
- Detailed Technical Answer:
    1. CRAG (`core/corrective_rag.py`): Grades retrieval relevance into Correct, Ambiguous, Incorrect.
    2. Self-RAG: Emits reflection tokens `[Is-Relevant]`, `[Fully-Supported]`.
    3. RRF (`core/hybrid_reranker.py`): Fuses dense and lexical ranks via $RRF(d) = \sum \frac{1}{k + r(d)}$.
    4. Cross-Encoder (`core/cross_encoder_reranker.py`): `ms-marco-MiniLM-L-6-v2` cross-attention.
    5. Context Optimizer (`core/context_optimizer.py`): Reorders chunks to combat attention degradation.
- Honest Qualification: Graph RAG and RAPTOR are NOT implemented in this codebase.

Q9: What is Reciprocal Rank Fusion (RRF) and why is it superior to score averaging?
- Simple Answer: RRF merges rankings based on positional rank rather than raw scores, avoiding the
  problem of combining scores that have different mathematical scales.
- Detailed Technical Answer: Cosine similarity ranges from $[0, 1]$, while Cross-Encoder logits
  range from $[-\infty, +\infty]$. Simple weighted addition $(\alpha S_1 + (1-\alpha) S_2)$ requires
  fragile min-max normalization. RRF assigns scores purely based on rank: $\frac{1}{k + r_i}$.
  With smoothing parameter $k=60$, RRF reliably ranks consensus documents at the top.

Q10: How does the system handle multi-turn conversational follow-ups?
- Simple Answer: Messages are persisted in SQLite. The `RetrievalRouter` resolves follow-up pronouns
  and retains prior preferences like language or explanation style across turns.
- Detailed Technical Answer: `main.py` auto-creates a conversation record on the first query.
  `ConversationService.get_conversation_history()` feeds up to 8 prior turns to the LLM.
  `RetrievalRouter.resolve_follow_up_references()` maps terms like "that", "the second point",
  or "in Tamil" to target entities from prior turns, maintaining conversational context.
- Code Reference: `core/conversation_service.py`, `core/retrieval_router.py`.

SECTION 4: PERFORMANCE & LATENCY QUESTIONS
--------------------------------------------------------------------------------

Q11: What were the primary latency bottlenecks and how were they eliminated?
- Simple Answer: Initial cold starts took 18s due to lazy PyTorch loading, and LangChain added 30s.
  We pre-warmed models in FastAPI lifespan, built `LocalEmbeddingAdapter`, and cached discovery calls.
- Detailed Technical Answer:
    1. Pre-warming: `EmbeddingService.get_model()` is invoked during `lifespan(app)` boot, reducing
       first-query latency from 18.5s to 0.42s.
    2. LangChain Elimination: Replaced generic LangChain HTTP retrievers with `LocalEmbeddingAdapter`
       and in-memory candidate extraction, dropping retrieval from 32s to 27.7 ms.
    3. Discovery Cache: Added 60s TTL cache for Qdrant collection documents (`_DOCS_CACHE`).
    4. Cryptographic Caching: `@lru_cache` on AES round-keys and MMR cloud proof paths.
    End-to-end query time dropped to 47.45 ms total.
- Code Reference: `main.py` lines 85-115, 1220-1230; `14_LATENCY_OPTIMIZATION_AND_PERFORMANCE_ENGINEERING.txt`.

Q12: What is the total cryptographic overhead of all five security gates?
- Simple Answer: Approximately 0.04 milliseconds (40 microseconds), or less than 0.1% of query time.
- Detailed Technical Answer: Vector search takes 27.71 ms, LLM generation takes 19.70 ms, AEAD
  decryption takes 0.0396 ms, and MMR verification takes 0.032 ms. Total Privacy RAG latency is
  47.45 ms compared to Ordinary RAG's 47.41 ms, proving cryptographic security introduces zero
  perceptible user lag.

SECTION 5: CHALLENGING REVIEWER & DEFENSE QUESTIONS
--------------------------------------------------------------------------------

Q13: Does encryption alone prove confidentiality if the server possesses the key?
- Simple Answer: No. Encryption protects data at rest in the vector store and in transit. A compromised
  backend server memory remains a vulnerability, which is an acknowledged architectural limitation.
- Detailed Technical Answer: AES-256-GCM protects against compromised vector database nodes, stolen
  storage snapshots, cloud provider subversion, and network sniffers. However, the verifier process
  in `main.py` holds the symmetric key to decrypt chunks before sending them to the LLM.
  True zero-trust server protection would require Trusted Execution Environments (Intel SGX / AMD SEV)
  or Fully Homomorphic Encryption (FHE), which are planned future enhancements.

Q14: Does high ciphertext entropy prove secure encryption?
- Simple Answer: No. High entropy proves uniform randomness, but security relies on the underlying
  hardness of the AES-256 permutation and key secrecy.
- Detailed Technical Answer: Shannon entropy measures byte frequency distribution. A pseudo-random
  generator can produce high entropy without cryptographic security. However, combined with NIST
  standard AES-256-GCM and unique 96-bit nonces, entropy $> 7.995$ bits/byte confirms absence of
  statistical plaintext leakage in the serialized ciphertext payloads.

Q15: Can an attacker infer document content from vector embeddings alone (Embedding Inversion)?
- Simple Answer: Black-box exact text reconstruction is mathematically near-impossible, though
  approximate semantic topics can sometimes be inferred.
- Detailed Technical Answer: `bge-small-en-v1.5` projects arbitrary-length text into 384 continuous
  dimensions. The mapping is many-to-one (lossy compression). While advanced research shows nearest
  semantic cluster tokens can be estimated, exact sequence reconstruction has a success rate $< 1.0\%$.
  To mitigate topic leakage, orthogonal query masking is implemented in `core/masking.py`.

Q16: Why not use Graph RAG or RAPTOR in this project?
- Simple Answer: Graph RAG and RAPTOR multiply ingestion latency by $10\times$ to $25\times$ and
  modify chunks recursively, which destroys exact cryptographic Merkle inclusion proofs.
- Detailed Technical Answer: Secure RAG requires bit-for-bit exactness to verify SHA-256 chunk hashes
  against the Enterprise Cloud MMR Root. RAPTOR recursively summarizes text trees, discarding the
  exact original character sequences. Graph RAG requires building entity triples with heavy graph
  databases like Neo4j, making sub-50ms latency impossible on consumer hardware.

Q17: What happens when an encryption key is rotated?
- Simple Answer: In the current version, key rotation requires re-encrypting chunks. Per-tenant KMS
  envelope encryption with Key Encryption Keys (KEK) is our planned enhancement.
- Detailed Technical Answer: Currently, a static 256-bit key is configured. Rotating the key requires
  re-running the ingestion pipeline on stored documents. In Section 23, we propose Envelope Encryption,
  where each document receives an ephemeral Data Encryption Key (DEK), and only DEKs are re-encrypted
  when the master KEK is rotated.
