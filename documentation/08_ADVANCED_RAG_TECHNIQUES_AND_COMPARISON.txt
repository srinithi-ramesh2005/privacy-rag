1. DEEP DIVE: IMPLEMENTED ADVANCED RAG TECHNIQUES
--------------------------------------------------------------------------------

A. Corrective RAG (CRAG)
   - Source Location: `core/corrective_rag.py` (Class: `CorrectiveRAGEngine`)
   - Functionality: Evaluates retrieval quality prior to generation. A lightweight retrieval
     evaluator checks whether retrieved context contains sufficient semantic overlap with query entities.
   - States:
       1. CORRECT: High confidence ($>0.70$). Context is directly synthesized.
       2. AMBIGUOUS: Medium confidence ($0.40 - 0.70$). Context is filtered with query expansions.
       3. INCORRECT: Low confidence ($<0.40$). Triggers automatic fallback/abstention.
   - Advantage: Prevents the model from fabricating answers when the retrieved context is irrelevant.

B. Self-RAG (Self-Reflective RAG)
   - Source Location: `core/corrective_rag.py` (Function: `generate_self_rag_reflection()`)
   - Functionality: Evaluates the generated response along three reflection dimensions:
       - `is_relevant`: Did the retrieval address the user query? (`[Is-Relevant:Yes/No]`)
       - `support_ratio`: Fraction of generated claims directly supported by decrypted context.
       - `reflection_token`: `[Fully-Supported]`, `[Partially-Supported]`, or `[No-Retrieval-Needed]`.
   - Advantage: Quantifies factual hallucination and provides an audit trail for compliance officers.

C. Reciprocal Rank Fusion (RRF)
   - Source Location: `core/hybrid_reranker.py` (Class: `HybridReranker`)
   - Mathematical Formulation:
       $$RRF(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$
     where $k=60$, $M$ is the set of rankers (vector similarity and lexical ranking), and $r_m(d)$
     is the rank position of chunk $d$.
   - Advantage: Eliminates score scale variance (e.g. Cosine Similarity in $[0, 1]$ vs Cross-Encoder logits
     in $[-\infty, +\infty]$) by ranking based strictly on positional rank.

D. Cross-Encoder Reranking
   - Source Location: `core/cross_encoder_reranker.py` (Class: `CrossEncoderReranker`)
   - Architecture: Pretrained `cross-encoder/ms-marco-MiniLM-L-6-v2`.
   - Functionality: Takes `(query, chunk_text)` as a concatenated input `[CLS] query [SEP] chunk [SEP]`
     and computes full multi-layer cross-attention between every query token and chunk token.
   - Advantage: Far more accurate than bi-encoder dot-products because tokens interact across layers.
   - Performance Trade-off: Evaluated on CPU in under 12 ms for top-20 candidate chunks.

E. Lost-in-the-Middle Context Reordering
   - Source Location: `core/context_optimizer.py` (Class: `ContextOptimizer`)
   - Theoretical Basis: Liu et al. (Stanford, 2023) proved that transformer LLMs suffer from severe
     attention degradation in the middle of long contexts (U-shaped performance curve).
   - Algorithm:
       Sort top $N$ chunks by relevance.
       Place chunk #1 at position 0 (start).
       Place chunk #2 at position $N-1$ (end).
       Place chunk #3 at position 1.
       Place chunk #4 at position $N-2$, etc.
   - Advantage: Ensures the most critical evidence receives maximum transformer self-attention weight.

F. Context Expansion & Stitching
   - Source Location: `core/hybrid_reranker.py` (Function: `expand_and_stitch_context()`)
   - Functionality: If top hits belong to the same document, checks whether neighboring indices
     `chunk_index - 1` or `chunk_index + 1` exist. Stitches continuous narrative text up to 6,000 chars.
   - Advantage: Solves the fragment boundary problem without storing bloated chunks.

2. COMPARATIVE EVALUATION AGAINST OTHER RAG PARADIGMS
--------------------------------------------------------------------------------

| RAG Paradigm        | Primary Strength                     | Main Weakness / Overhead             | Used in Project? |
|:--------------------|:-------------------------------------|:-------------------------------------|:-----------------|
| Standard RAG        | Simple, low latency                  | Plaintext leakage, tamper-vulnerable | Baseline Only    |
| HyDE                | Improves keyword-sparse queries      | Generates hallucinated search terms  | PARTIAL (MQE)    |
| CRAG                | Filters out irrelevant retrievals    | Extra grading step                   | YES (core/)      |
| Self-RAG            | Generates verifiable audit tokens    | Additional evaluation overhead       | YES (core/)      |
| Graph RAG           | Multi-hop entity relationship reasoning| High ingestion latency, complex schema| NO               |
| RAPTOR              | Multi-tier hierarchical summaries    | Expensive recursive tree building    | NO               |
| SECURE RAG (Ours)   | 5-Gate Cryptographic Verifiability   | Small crypto overhead (~0.04 ms)     | YES (Complete)   |

Why Graph RAG and RAPTOR were not selected:
  Graph RAG requires constructing entity-knowledge graphs with Neo4j or Cypher queries,
  multiplying document ingestion latency by $10\times$ to $25\times$.
  RAPTOR recursively summarizes text trees, which permanently alters and compresses chunks,
  making exact cryptographic Merkle inclusion proofs impossible because the original text
  is lost in summarization. Secure RAG prioritizes exact cryptographic verifiability.
